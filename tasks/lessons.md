# Lessons

Gotchas found while building. Append only; never rewrite history. Newest at the bottom.

## Build environment

- **Composer over the agent proxy.** `composer install` fails to authenticate against `api.github.com`; `composer install --prefer-source` (git over the proxy) works. As root, set `COMPOSER_ALLOW_SUPERUSER=1`.
- **No `rsync`.** Copy a plugin into a test site with `cp -r`; a script that expects `rsync` copies nothing and the old code keeps running.
- **The CLI keeps no response headers.** `headers_list()` and `http_response_code()` are empty in PHP's CLI, so headers cannot be asserted from a script that runs WordPress as a CLI process. Capture redirects and statuses with the `wp_redirect` and `status_header` filters, and check real headers over HTTP (`php -S` plus `curl -i`).
- **A test that echoes before WordPress sends headers causes "headers already sent".** Collect markers and print them in a shutdown function.
- **Match our own queries by table and option name, not by substring.** WordPress's `cron` option contains our hook names, so any query that rewrites it matches `blt_activity_log`.
- **Integration tests leave state behind.** Make each one start from what it needs (delete the option, remove the theme mod, delete the users) or it passes once and fails on the second run.

## WordPress behavior

- **`wp_get_post_revision()` takes its argument by reference.** `wp_get_post_revision( (int) $id )` is a fatal error ("could not be passed by reference"); assign to a variable first. Found only by rendering a real entry that had a revision; a row built by hand did not reach it.
- **`WP_User::set_role()` fires `remove_user_role` and `add_user_role`, then `set_user_role`, after the roles are already changed.** Reading the user's roles inside those hooks gives the new state, so a "before" computed there is wrong (an edit from editor to author read "author, editor" to "author"). Read the capabilities user meta (`{$wpdb->get_blog_prefix()}capabilities`) before (`update_user_meta`) and after (`updated_user_meta`, `added_user_meta`), and ignore the three role hooks. A new account's role arrives the same way, before `user_register`, so the creation entry absorbs it.
- **`WP_Ajax_Upgrader_Skin` extends `Automatic_Upgrader_Skin`.** Test for the Ajax skin first or every screen update is classified as automatic.
- **A theme switch finishes on the next request.** `after_switch_theme` remaps menu locations and widgets; that must not be logged as someone editing menus. It also writes `theme_switched`, `theme_switch_menu_locations`, `template`, `stylesheet` and `current_theme`, which the "any option" scope would otherwise log.
- **Deleting a post fires an `updated`-looking save first.** Guard it (the module keeps a `$deleting` flag), and ignore the `__trashed` slug rename on trash.
- **`add_action` wrappers cannot wrap filters.** `BLT_Activity_Log_Module_Base::listen()` calls the callback and returns nothing, which would turn a filter's value into `null`. It is for actions only.
- **`added_option` fires only when the option did not exist.** A test that adds an option passes the first time and logs nothing the second.
- **`update_option()` with an unchanged value fires nothing**, so a settings test that sets the value it already has proves nothing. Reset the option first.
- **`wp_privacy_anonymize_ip()` keeps the first 64 bits of an IPv6 address** (`2001:db8:85a3:1::`), not the first three groups.
- **The sign-in context is decided by `$pagenow`**, which WordPress recomputes while loading. Set it inside the request, after load, in a test.
- **A visitor creating a tag is a real change.** Creating a new term from a public request is logged (only meta and term relationships on posts are skipped on the front end). Pre-create the term when a test means to exercise only the relationship.
- **A page view can write.** WordPress rebuilds `rewrite_rules` on the first public request after they are cleared. That write must not be logged, in either scope.
- **Hook signatures at the 6.0 floor** were read from WordPress 6.0 source before the modules were written. Of note: `wp_after_insert_post` has four arguments; `set_object_terms` has six, including the old term taxonomy ids; `delete_user` has three; `wp_create_application_password` has four; `upgrader_process_complete`'s `hook_extra` differs for install, update and bulk.

## Logging design

- **`absorb` must take every listed sibling, not the first.** A new account has profile-meta changes (`updated`) and a role change waiting when `user_register` fires; absorbing only the first match left the other as a stray entry. An earlier `updated` or `role_changed` yields its action to whatever it turns out to belong to (`BLT_Activity_Log_Coalescer::DETAIL_ACTIONS`).
- **Coalescing applies to a second test edit too.** Two edits by one person inside 60 seconds are one entry (with the later revision id); age rows between steps in a test that wants two.
- **A map that appears or disappears is walked key by key.** `values( 'o', [], [ 'nested' => [ 'x' => 1, 'client_secret' => 's' ] ] )` must report `o[nested][x]` and a hidden `o[nested][client_secret]`, not one blob; and deleting an option holding a map reports each key it had.
- **Never trust the shape of stored details.** Other plugins write entries through `blt_activity_log_record` and rows outlive the code that wrote them. The Redactor drops a non-array `changes` or non-scalar `summary` on the way in, and `Formatter::details()` normalizes everything on the way out, so no screen guards against it.
- **The ignore list needs more than the spec's.** Besides the spec's list, "any option" scope logged WordPress's own side effects until these were added: theme-switch bookkeeping, `*_children` caches, `wp_calendar_block_has_published_posts`, `db_version`, `fresh_site`, `finished_*`, `recently_edited`, `*user_roles` and `adminhash` (a confirmation token). A test asserts the core allowlist and the ignore list never overlap.

## Admin UI

- **WordPress's responsive list table hides only the columns after the primary column.** The primary column is the first by default; columns before it stay visible on a phone with their `::before` labels overlapping the content. Keep the primary column where the content you want shown first is, or hide those labels with a selector at least as specific as WordPress's (`.wp-list-table tr:not(.inline-edit-row):not(.no-items) td:not(.check-column)::before`), and do not set fixed column widths below 783 px.
- **A long category label wraps inside its pill.** Give the pill `white-space: nowrap` and put the action label on its own line.
- **List table markup:** rows have no id; pagination uses single-quoted attributes. Match with a regular expression that allows both quote styles.
- **Rendering synthetic rows hides bugs.** Build test entries from real events (create the post, update it, delete it) and open every one on the detail screen.

## Second review round (retention cap, dump)

- **`wpdb::get_results()` returns an empty array when the query fails, not `null`.** `query()` flushes the result first, so a failed query leaves `last_result` empty. A streaming loop that stops on "no rows" cannot tell the end of the data from a timeout; check `$wpdb->last_error` after the call (`Query::export_batch()` now returns `null` on error and the file gets an `ERROR` line saying it is incomplete). My first attempt tested `is_array()` alone and would never have fired; the failure had to be forced with a `query` filter to find out.
- **Log a download before it starts, not after it finishes.** A cancelled or failed download never reaches the code after the loop, so an export that handed over data would leave no record. The entry is written first and the file is bounded to the newest id as of that moment, so it is one consistent snapshot and does not contain its own log entry.
- **A dump reads every column, including `details` (up to 64 KB per entry).** Use a smaller batch than the export (250 against 1,000) so a run of large entries cannot exhaust memory.
- **A form value that means nothing must not be turned into something.** `absint()` turned a typed `-7` into 7 days of retention, and 0 or text was silently ignored while the screen said "saved". Non-numeric, zero and negative values are refused, over-365 is capped, and the notice says what retention actually is.
- **There is no "keep forever".** Retention is 1 to 365; 0 in storage or in the wp-config constant reads as the 90-day default, so a bad value can never mean "delete everything older than a day" or "never delete".
- **User meta is network-wide.** The per-page screen option is plain user meta, so `uninstall.php` skips deleting it on multisite rather than wiping other sites' setting.
- **Spreadsheet escaping changes the data.** Prefixing a cell that starts with `= + - @` with an apostrophe is right for a file people open in a spreadsheet, but it means the file is not byte-faithful. The Settings card says so.
- **Test tooling:** a CSV parsed with `fgetcsv()` needs the escape argument set to `''` to match `fputcsv( ..., escape: '' )`; the harness prints blank lines after the response body, which parse as one-cell rows; PDO returns integer columns as PHP ints.

## Third review round (four independent reviewers over the committed code)

- **`upgrader_process_complete` fires after a failed update too, and a bulk update fires it once with every plugin it was asked about** (up to date, failed, or never reached). Do not trust the hook as proof an update happened: compare the version now on disk with the one before, and leave out any that did not move (an upload may legitimately replace a plugin with itself). A skipped item must also stay out of the snapshot refresh, or a plugin that really changed would never be reported.
- **Refresh only what a logged change touched.** Re-storing the whole snapshot after every plugin update silently absorbed unrelated out-of-band changes (a Composer deploy of plugin B at 02:00 vanished when an admin updated plugin A at 09:00). `Snapshot::refresh_keys()` moves only the named plugin, theme or core version.
- **`get_plugins()` and `wp_get_themes()` cache with no expiry.** With a persistent object cache they answer with the list from before an FTP or Composer deploy, so the daily snapshot saw nothing and stored the stale list as the new baseline. Clear both caches (`wp_clean_plugins_cache( false )`, `wp_clean_themes_cache( false )`) before reading, and after `delete_plugins()`, which leaves the list cached.
- **A switched-off category must stay quiet everywhere.** The daily snapshot still reported every plugin, theme and core update as `changed_externally` for a module the owner had disabled. It now records only for enabled modules and still moves the baseline.
- **Revert detection needs a fingerprint, not a length.** Treating "same character count and no block change" as "edited and edited back" dropped two real edits ("Monday" to "Friday" to "Sunday") and left no audit row. A content summary now carries a short hash of the content before and after, so a revert is exact; rows without hashes are never dropped on a guess.
- **WordPress can report one save twice, or in the wrong order.** A `save_post` callback that saves the post again fires `wp_after_insert_post` for the inner save first, and the outer save then reports a stale before and after; the Site Editor's REST controllers fire the hook again after saving. Merge by chain, not by arrival order: a later change that ends where the earlier began came first, and an identical content event counts once.
- **Concurrent requests merge into the same row.** Read, merge in PHP and `UPDATE ... WHERE id` loses the other request's changes. The write now names the version it read (`occurrences` and `last_at`), a loser reads the winner's row and merges on top (three tries), and a save that keeps losing becomes its own row instead of being lost. `$wpdb->update()` returning 0 is a lost race, not a success.
- **One bad entry must not cost the others.** Per-entry isolation in the flush; a refused multi-row INSERT is retried row by row; a throwing `blt_activity_log_logged` listener does not stop later rows; strings a filter lengthens are cut to their columns again (strict mode fails a whole multi-row INSERT on one over-long value); a malformed `created_at` falls back to now.
- **A key pattern has to survive how people actually name things.** `accessToken`, `clientSecret`, `smtp.password`, `Client Secret`, `passwords`, `api_keys`, `nonce_key` and `logged_in_key` all escaped the spec's pattern. Keys are now normalized (camelCase split, dots and spaces to `_`) and the pattern takes plurals and the WordPress key names. WordPress's generated keys and salts (stored as options when wp-config lacks them) are also never logged.
- **An option this plugin writes itself can be logged as someone's setting change** in the "any option" scope: `blt_activity_log_db_version` was. Every own option is on the ignore list.
- **`dbDelta()` can fail quietly.** Stamping `blt_activity_log_db_version` regardless meant a missing CREATE privilege became permanent (no retry, every write failing). The version is recorded only when the table is really there (compared case-insensitively: `lower_case_table_names` can change the case SHOW TABLES returns).
- **Terms and meta have scope too.** `set_object_terms` fires for any object type (a BuddyPress member type with the same number as a page was logged as a page edit); with `$append` WordPress passes no "before", so use `added_term_relationship` to see what was really new; autosaves reach the term and meta hooks even though the post hook ignores them; anonymous AJAX and REST calls (a view counter) are visitors too; and while a post is first published `get_post()` still says `auto-draft`, so its terms and meta were dropped from the created entry (read the row).
- **Taxonomies and post types need a boundary.** A block theme's `wp_theme` and `wp_template_part_area` terms, WooCommerce orders and ACF field groups were all logged. Terms follow `show_ui`; orders and ACF definitions are excluded by default (a site can add them back with `blt_activity_log_post_types`). Caching the post-type list as soon as `init` *starts* cached a partial list; wait for `wp_loaded`.
- **Order of writes inside `switch_theme()`:** `template` and `stylesheet` change, then the new theme's mods are created, and only then does `switch_theme` fire. Anything that skips theme-mod writes during a switch has to start at the stylesheet change, not at the action. Deleting a nav menu removes its term before clearing the location that pointed at it, so remember its name beforehand.
- **A clear must be bound to its preview.** The confirm used to recompute "everything" at confirm time, so entries written since the preview were deleted uncounted, and a confirm with no preview deleted at all. The preview carries the newest id it counted; the delete stops there; "older than a date" refuses a date that has not started (it would take the `log_cleared` record and everything after with it).
- **"Older than a day" in a time zone where DST starts at midnight** (Havana, Beirut, Cairo, Santiago, São Paulo): adding a day to a local midnight that does not exist lands on 01:00 and keeps it. Work out the next date as a calendar date first, then take its local midnight.
- **`wpdb` pitfalls in the admin:** a huge `paged` overflows `(page - 1) * per_page` into a float that formats as `OFFSET 0`, so cap it (and let `WP_List_Table::get_pagenum()` hold it to the last page once the total is set); `substr()` cuts multibyte text mid-character into invalid UTF-8 that matches nothing, so use `mb_substr()`; an Activity filter regex narrower than `sanitize_key()` silently ignores valid keys with hyphens.
- **Do not label by substring when you mean an object.** "All activity for this item" searched by label and matched every other item containing the text. It now filters by object type plus id or key.
- **Dates stored in site time must not be formatted as UTC.** `post_date` is site-local; running it through the UTC-to-site converter shifted every shown date by the offset.
- **A normalizer that rebuilds an array can silently drop keys.** The `note` on a password change (set, changed, removed) was lost when the details were normalized for display, so the text for it was never shown. Keep a test that round-trips every key the writers produce.
- **Do not read the reviewers' words as findings: verify.** Several reports were right in substance and wrong in detail (a repro that only works for a first-ever switch to a theme, a function that already had the guard). Each one was reproduced or traced before a fix, and two were declined (see `tasks/todo.md`).
